## Начало работы
### Клонирование репозитория
```bash
git clone
```

### Настройка виртуального окружения и установка зависимостей

```bash
make install
source venv/bin/activate
```

`make install` создает виртуальное окружение `venv/` и устанавливает все пакеты из `requirements.txt` и `requirements-dev.txt`.
### Запуск сервера
```bash
make run
```
Сервер доступен по адресу: http://127.0.0.1:8000

## Работа с Git

### Ветки
Ветки создавать от Issue:
```text
1. Создаёшь Issue на GitHub (например, "Добавить модель Pet")
2. GitHub автоматически присваивает номер (например, #12)
3. Создаёшь ветку от develop с номером issue
```

| Ветка       | Назначение                |
| ----------- | ------------------------- |
| `main`      | Стабильная версия         |
| `develop`   | Основная ветка разработки |
| `feature/*` | Ветки для новых функций   |

### Правила
- Создавай ветку от `develop`
- Формат имени: `feature/краткое-название`
- Коммиты должны быть маленькими и осмысленными
### Пример

```bash
git checkout develop
git pull origin develop
git checkout -b feature/add-pet-model
git add .
git commit -m "feat: add Pet model"
git push origin feature/add-pet-model
```

## Документирование изменений и Pull Request
### Документирование в процессе разработки

Каждое изменение в проекте должно сопровождаться документацией. Это позволяет команде понимать, что было сделано и почему.
#### Obsidian как среда для документации
Все файлы документации хранятся в репозитории в папке `docs/`.
Настройка Obsidian:
1. Установить Obsidian
2. Открыть папку `docs/` как хранилище
3. Все файлы автоматически синхронизируются через Git

Папка `.obsidian/` добавлена в `.gitignore` — настройки редактора остаются личными.

#### Командная документация (репозиторий)
Готовая документация сохраняется в папке `docs/`:
- `ER_diagram.drawio` — схема базы данных
- `DECOMPOSITION.md` — декомпозиция задач
- `MODELS.md` — описание моделей
- `ARCHITECTURE.md` — схема слоев
- `INTERACTION_FLOW.md` — схема взаимодействия
- `wiki/` — руководства и инструкции

#### Как документировать изменения

При добавлении новой фичи:

1. Создаешь черновик в Obsidian
2. Пишешь реализацию
3. Обновляешь документацию в `docs/`
4. Включаешь обновления в тот же PR

### Pull Request

#### Создание PR
1. Открыть репозиторий на GitHub
2. Нажать "Compare & pull request"
3. Base: `develop`, compare: `feature/название_ветки`
4. Заполнить описание по шаблону
5. Нажать "Create pull request"

#### Шаблон PR

В репозитории настроен шаблон `.github/PULL_REQUEST_TEMPLATE.md`:

```markdown
## Что сделано?
- [ ] 

## Как проверить?
1. 

## Скриншоты (если есть)
!

## Связанные задачи
Closes #
```

При создании PR шаблон подставляется автоматически. Разработчик заполняет все разделы.

#### Требования к PR

- Название отражает суть изменений
- Описание заполнено по шаблону
- CI проходит (все статусы зеленые)
- Получен аппрув от одного члена команды
- Все комментарии закрыты

#### Как связать PR с задачей

В описании PR укажи номер задачи:

```markdown
Closes #12
```

После вливания PR GitHub автоматически закроет задачу.

#### Процесс ревью

1. Автор создает PR
2. Назначает ревьювера
3. Ревьювер проверяет код
4. Если есть замечания — оставляет комментарии
5. Автор исправляет и обновляет PR
6. Ревьювер ставит аппрув
7. PR вливается в `develop`
8. Ветка удаляется

---

### После вливания PR

1. Убедись, что ветка удалена (GitHub предлагает удалить)
2. Обнови локальную `develop`:

```bash
git checkout develop
git pull origin develop
```

3. Проверь, что документация в `docs/` актуальна
4. Если изменения касаются архитектуры — обнови схемы в `docs/`
5. Сделай скриншот, если добавился новый экран, и положи в `docs/screenshots/`

## CI/CD (GitHub Actions)

При каждом Push и Pull Request запускаются проверки:

| Этап | Что проверяет |
|------|---------------|
| Линтеры | Стиль кода (flake8, isort, black) |
| Сборка | Корректность проекта |
| Тесты | Прохождение тестов |

## Декомпозиция: приложение `profile`

Служебное приложение - без своей модели, только логика чтения и комбинирования данных из `users` и `pets`.


| Задача                                                                                          | Часы | Ответственный |
| ----------------------------------------------------------------------------------------------- | ---- | ------------- |
| View страницы профиля (данные User: display_name, avatar, bio/info + список Pet владельца)      | 1    | Димас         |
| Запрос списка питомцев юзера (Pet.objects.filter(owner=user))                                   | 0.5  | Димас         |
| Шаблон страницы профиля (био: аватар, имя, инфо + список карточек питомцев: аватарка, имя, пол) | 1.5  | Димас         |
| Карточка "Добавить питомца" в конце списка (ссылка на страницу создания питомца из `pets`)      | 0.5  | Димас         |
| Проверка существования профиля (404, если юзера с таким id не найден)                           | 0.5  | Димас         |
| Тесты: страница профиля отдаёт статус 200 (доступна и гостю)                                    | 0.5  | Степан        |
| Тесты: список питомцев на странице соответствует реальным питомцам юзера                        | 1    | Степан        |
| Тесты: профиль юзера без питомцев отображается корректно (пустой список)                        | 0.5  | Степан        |
| Тесты: несуществующий юзер (404)                                                                | 0.5  | Степан        |


**Итого: 6.5 часов**

### Примечания

- Своей модели нет - вьюха читает `User` (из `users`) и `Pet` (из `pets`), ничего не создаёт и не хранит сама.
- Карточка питомца в списке - заглушка на будущее: сейчас аватарка + имя, можно добавить что угодно
- Кнопка "создать питомца" физически размещается на этой странице, но ведёт на страницу создания питомца из приложения `pets` - сама логика создания здесь не реализуется.
- Редактирование bio (текстовых полей User) - не здесь, а в `users` (форма редактирования профиля).

- Календарь ДР - персонализированный (только питомцы из подписок текущего юзера), поэтому логика живёт в `feed`, а не в `pets`
- Рейтинг - глобальный (среди всех питомцев/блогов платформы), не зависит от подписок юзера; единица рейтинга - питомец, метрика суммируется по всем его постам.
- Критерий сортировки пока не выбран, но может быть любой. Логику отображения никак не затргивает
- Карточка поста в ленте переиспользует шаблон из `posts`, здесь только список и сортировка, не отрисовка самого поста с нуля.

### Примечания

- Своей модели нет - рекорды/очки существуют только в рамках клиентской сессии (JS-переменная), при обновлении страницы обнуляются. Персистентность (сохранение рекордов в БД, лидерборд по играм) - вне текущего скоупа, отдельная будущая декомпозиция при необходимости.
- Игры не привязаны к конкретному питомцу пользователя - общие для всех, доступны в том числе гостям (login_required не нужен, если явно не потребуется иное).
- Django здесь выполняет роль тонкой обёртки: отдаёт HTML-контейнер и статические JS/CSS-файлы игры; вся игровая логика - на клиенте, бэкенд её не видит и не валидирует.
- Часы на "Игру 1"/"Игру 2" - примерные и сильно зависят от сложности конкретной механики; список игр (2 - не финальный, чисто для примера структуры декомпозиции).
- Если позже потребуется сохранение рекордов - добавится модель `GameScore` (user_id, game, score, created_at) + соответствующие View/тесты, это отдельный блок задач поверх текущего.
